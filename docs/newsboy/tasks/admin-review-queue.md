# Task: human sensitivity review gate for scheduled generation

## Why

[launch-plan.md](../launch-plan.md#phase-0-private-alpha) names this
explicitly:

> Scheduled generation currently publishes automatically, so a documented
> human sensitivity review remains a public-launch blocker until the
> pipeline enforces that gate.

This is the highest-priority item on the list — it's a named launch
blocker, not a nice-to-have.

## Current state (for context)

- The admin-UI generation path (`admin.generate.tsx` →
  `lib/admin/publish.ts::publishCandidate`) already requires an operator to
  pick a candidate and explicitly publish — that path is effectively
  reviewed today.
- The scheduled path
  (`.github/workflows/newsboy-generate.yml` → `pnpm newsboy:generate` →
  `generation-runner.ts` → `generatePuzzleForGame`) publishes a passing
  candidate directly to `games_puzzles` with no human step in between. The
  deterministic checks in
  [candidate-generation.md](../candidate-generation.md) run, but nothing
  human-reviews sensitivity (e.g. a technically-valid answer sourced from a
  tasteless or harmful story) before it's live.

## Scope

- Add a `pending_review` (or similarly named) state between "candidate
  passed automated checks" and "live in `games_puzzles`" for
  scheduler-originated generation.
- Surface pending puzzles in `/admin` (extending the existing
  `admin.generate.tsx` / `admin.dates.$date.tsx` surfaces) with a clear
  approve/reject action, reusing `recordAdminAction` /
  `game_admin_actions` for the audit trail exactly as every other operator
  write already does.
- Decide and document the SLA: puzzles are generated the night before
  (22:00 UTC / 23:00 UTC gap-fill per architecture.md), so there needs to be
  a realistic window for a human to review before the puzzle needs to go
  live for the next local day, across all player timezones the site
  protects against (UTC and `America/Los_Angeles`, per architecture.md's
  live-puzzle protection note).
- A rejected pending puzzle should behave like a failed generation attempt
  (date stays missing, eligible for the next gap-fill run), not silently
  vanish — consistent with "a failed date stays empty... it does not
  quietly pull in an archive puzzle."

## Implementation notes

- This likely means `generatePuzzleForGame` writes the winning candidate to
  `games_puzzles` with a new not-yet-live marker (or a parallel
  "pending approval" table/row) instead of `publishedAt` being immediately
  set, and the serving path (`resolveActivePuzzle`) must never resolve an
  unapproved puzzle — get this wrong and the gate does nothing.
- Approval action should reuse `publishCandidate`'s shape/audit pattern
  where possible rather than inventing a second publish code path.
- `pnpm newsboy:health-check` currently marks `DEGRADED` when tomorrow has
  no puzzle — decide whether "pending review, not yet approved" should also
  count as degraded/at-risk so an unreviewed puzzle doesn't silently miss
  its window.

## Acceptance criteria

- A puzzle generated by the scheduled workflow never becomes visible to
  players (`resolveActivePuzzle`) until an operator explicitly approves it.
- The admin console shows a clear, actionable pending-review queue, not
  just raw generation-run records.
- Every approval/rejection is recorded via `recordAdminAction` with the
  reviewing operator's identity, matching the existing audit pattern.
- The manual admin-UI generate-and-publish flow is unaffected (it was
  already effectively reviewed).

## Out of scope

- Automated sensitivity classification (ML-based content moderation) — this
  task is specifically the human-in-the-loop gate the launch plan asks for,
  not a replacement for one.
